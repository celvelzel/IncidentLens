# IncidentLens 优化路线图

更新时间：2026-11-01（Asia/Shanghai）

这份路线图回答三个问题：

1. 当前系统已经证明了什么，还没有证明什么？
2. 后续应该先做哪些工作，为什么按这个顺序做？
3. 每项工作由谁推进，做到什么程度才算完成？

当前主架构是 `dynamic`：根据证据缺口动态选择专家，由 Merge 合并并校验共享证据，再由确定性的
FinalizeGate 决定是否接受根因；默认不调用独立的 LLM Verifier。`full` 保留为“在 Dynamic 上
额外加入独立复核”的消融对照。

本文描述的是**计划与验收方法**，不代表所有改进已经实现，也不把开发集上的收益提前写成已证实结论。
本轮已完成两项并标注在对应章节：P0-B 的证据不足成本护栏（实验开关，默认开启）和 P0-C 的
开发案例扩容（新增 `causal-world-v2-hardened` 血统，10 → 36 例）。其余条目仍是计划。

## 一分钟摘要

- 当前选择 `dynamic` 的直接理由，是在 10 个开发案例上，它的暂定质量与 Single、Full 相同，
  但平均耗时和 Token 更低。
- 这还不是“Dynamic 在统计上显著更优”或“可以保证生产准确率”的结论。现有数据只有 10 个
  开发可见案例、每组合一次运行，标签也仍是候选状态。
- 后续优化的主线不是继续增加 Agent，而是先解决三个基础问题：结果可复算、搜索范围有依据、
  标签和测试集可信。
- 然后优先减少每轮传入模型的重复内容，并让系统用更少、更有区分价值的调查完成判断。
- 按需 Verifier、提供商兼容性、模型分工、缓存和并发放在后面；它们是待验证方案，不是当前默认目标。

如果只看一个指标，当前优先改善的是：**在证据不足时，能否更早判断“继续查也不会改变结论”，
同时不把本来可以查清的案例过早判为弃答。**

## 优先级怎么读

| 级别 | 含义 | 默认处理方式 |
| --- | --- | --- |
| **P0** | 不做就无法可靠比较后续收益，或会直接影响质量与实验可信度 | 先启动，作为其他优化的共同基础 |
| **P1** | 已有明确现象支持，最可能改善全流程效率 | P0 基础可用后并行实验，分别验收 |
| **P2** | 有潜在价值，但触发条件、案例或实现尚未验证 | 在代表性案例和独立实验条件准备好后开展 |
| **P3** | 成本或延迟探索，当前证据不足 | 等架构稳定后逐变量测试 |

同一优先级内的排序依据是：证据强度、预期收益、质量风险、实现成本和依赖关系。
“重要”不等于“现在做”；“能实现”也不等于“值得默认开启”。

## P0 · 先建立可信的比较基础

### P0-A · 统一评测账本与可观测性

**为什么做**

后续每项优化都会声称“更便宜”“更快”或“更准确”。如果各项报告从不同日志、不同分母或不同
成功口径计算，团队无法判断收益来自改进还是统计方式变化。

**现状**

trace、verification 与 measured-usage 已记录请求、工具、Token、终止和失败；查询历史与数据库覆盖
已有基础实现，见
[`evidence_board.py`](../../src/incident_lens/orchestration/evidence_board.py)。
这项工作主要是补齐、统一和验证，不另建一套与现有记录冲突的计数器。

**工作内容**

1. 定义批次级和逐案例级的共同字段：计划槽位、技术完成、质量结果、首次完成、最终完成、
   实际 HTTP 请求、逻辑调用、修复、工具、输入 / 输出 Token、调查耗时、终止原因和触发原因。
2. 把失败、中断、预算终止和正常弃答分开。所有计划槽位都进入技术完成率与成本分母；正常弃答
   只有在 oracle 规定该案例不可识别时才算正确。
3. 分别报告“最终成功成本”和“包含所有尝试的成本”。未知 usage 保持未知，并报告数据完整率
   或已知下界，不能填零。
4. 将调查耗时与批次排队、恢复等待分开。并发案例的耗时之和不能当作实际批次墙钟。
5. 记录原始条件名、运行时名称、代码 / 提示 / 协议版本、模型、公开输入哈希与 repeat。
   别名可以统一显示，但不同版本、模型或策略不能混成同一个实验条件。
6. 按轮记录新增证据、覆盖范围变化、门控缺口变化与动作。它们是可观察的诊断信号，
   不能包装成经过校准的“信息增益”。
7. 让批次报告、Web 与后续图表从同一份派生结果读取。先保证计数可复算，再改展示。

**不要改变**

- 不改历史冻结结果，不把失败 attempt 删除或择优替换。
- 不修改既有 oracle 或评分定义来让新结果看起来更好。
- 不在原始 trace 中记录私有标签或敏感凭据。

**完成标准**

- 任一批次可以从原始事件、verification 与 usage 重新生成逐例表和聚合表。
- 正常定稿、正常弃答、修复成功、失败和中断均有测试样例。
- 报告中的同一指标在批次报告、Web 与复算脚本中数值一致。
- 历史编码问题只在新分析目录中派生显示字段；冻结 JSON 保持原样。

**交付物**

指标定义、字段映射、复算脚本、测试结果和一份新批次报告示例。

### P0-B · 查询覆盖、去重与搜索收敛

**为什么做**

系统需要区分两件看似相同、含义不同的事：

- 已经完整查过某个范围，而且没有记录；
- 还没有查、只查了一部分、分页没结束，或者查询失败。

把前者误认为“服务正常”会错误排除原因；把后者误认为“已经查完”会过早弃答。
相反，如果完整范围已经查过，仍反复调查同一范围，则会增加成本而不一定增加证据。

**现状**

[`graph.py`](../../src/incident_lens/orchestration/graph.py) 已有任务签名、部分完成范围去重、
预算限制和模型主动弃答；Coordinator 提示也要求在没有新的判别检查时考虑弃答。
优化应增强这些机制，而不是只增加“连续几轮没进展就停止”的口号式规则。

**本轮已实现的成本护栏（2026-11-01，实验开关，默认开启）**

按上面第 5、6 条实现了一个**可测量的**版本，并把“口号式规则”落成确定性判据：

- `WorkflowOptions.evidence_gap_rounds`（默认 **5**，`0` 关闭）。`InvestigationRun` 每轮在
  `coordinate` 里调用 `record_evidence_gap(state)`：若本轮没有任何候选获得
  `cause_discriminator`，连续计数 +1；一旦出现决定性观察则清零。
- 计数达到阈值时，`coordinate()` 写入 `stop_reason="INCONCLUSIVE"`、发出
  `INVESTIGATION_EVIDENCE_EXHAUSTED`（附成本快照），路由到 `report`。
- 它**只决定预算**，不改变什么算“可接受”：`FinalizeGate`、`grounding_errors`、
  `BEST_SUPPORTED_AVAILABLE` 全部不变，所以它既不会把可查清的案例判成正确弃答，
  也不会让本来该弃答的案例变成错误归因。`fixed` 变体不启用（它本来就不做后续轮次）。
- 阈值不是拍脑袋定的，而是用
  [`recalibrate.py`](../../analysis/wp_d/reports/evidence-gap-calibration-20261101/recalibrate.py)
  在**冻结的 WP-D 轨迹**上只读重放该判据得到的：可识别案例的最大连续缺口轮数为 3
  （single / dynamic / full 三个变体都是 3），因此 4 是首个零误报值；mock 套件在不受轮次上限
  限制时峰值为 4，所以取 5 留一格余量。详见
  [校准报告](../../analysis/wp_d/reports/evidence-gap-calibration-20261101/)。

**必须一起读的三条限制**

1. `configs/system.yaml` 目前是 `max_rounds: 4`。阈值 5 在该默认配置下**永远不会触发**——
   轮次上限先到。要在默认配置里生效，必须同时调高 `max_rounds`，或把
   `investigation.evidence_gap_rounds` 调低；后者会重新引入误报风险（见上表：阈值 3 在
   3005 上误报）。
2. 本轮的收益是**从冻结轨迹上重放得到的估计**，不是新批次实测。在 th=5 下：3003 的 Token
   从 268,375 降到 150,355（−44.0%），3008 从 274,794 降到 214,669（−21.9%），
   Dynamic 十例合计 −12.3%。**3008 未达到下文“单例 ≥25%”的目标，批级 ≥10% 的目标达到。**
3. 重放只覆盖动态组已有的 10 个案例，没有覆盖“延迟才出现关键证据”的案例；这正是 P0-C
   要求补充的场景。护栏在那种案例上是否过早弃答，本批**无法回答**。

**工作内容**

1. 建立统一的查询范围签名，至少包含工具、有效参数、服务、时间窗、过滤条件、
   分页 / 截断状态和数据快照。
2. 只有在工具语义、权限和数据版本允许时，才判断一个范围是否被另一个范围完整覆盖。
   失败、部分完成、游标未结束或数据已变化的查询不能算完整覆盖。
3. 复用 `query_history` 与 `database_coverage`，区分 `unqueried`、`complete_empty`、
   `complete_with_records`、`failed` 和 `partial`。
4. 派单前移除已知完整覆盖、在当前数据快照下不会产生新信息的子查询；同时保留尚未读取的
   配置 diff、未完成分页、新的时间范围和仍可能区分候选根因的检查。
5. 把“连续若干轮没有新证据”作为重新评估信号，而不是自动停止条件。停止前需要说明：
   已覆盖哪些范围、还剩哪些关键缺口、为什么没有可执行的新检查，以及为何不先定稿。
   **本轮已按此实现**（见上方“本轮已实现的成本护栏”），并改为以“没有任何候选获得
   `cause_discriminator`”为判据，而不是笼统的“没有新证据”——后者会把“又收到一条同症状
   记录”也算成有进展，从而永远不触发。
6. 若引入 `INVESTIGATION_EVIDENCE_EXHAUSTED` 等新事件或阈值，先作为版本化实验开关。
   补齐 trace、checkpoint / resume、事件消费者和旧结果兼容后再评估默认值。
   **本轮已实现**：事件已加入 `evaluation/termination.py` 的已知事件集，trace 与 resume
   能安全忽略未知事件；默认值由上面的轨迹重放确定，而不是凭经验设定。

**不要改变**

- `grounding_errors`、`finalize_errors`、引用与身份校验和
  `BEST_SUPPORTED_AVAILABLE` 判定保持不变。
- 提前停止同样可能造成错误弃答，因此必须和质量回归一起验收。
- 规则不得读取 oracle，不得按 incident 编号触发，也不得为已知案例写特判。

**完成标准**

- 新增范围包含、分页、失败后恢复、延迟关键证据和 resume 的测试。
- 3004、3005、3010 在 Dev10 回归中仍能正确归因。
- 在新案例集上，错误弃答没有超过运行前设定的质量容忍界限。
- 每条提前停止都有结构化理由和成本快照，可以复算。
- 开发目标可在运行前冻结为“两个高成本弃答案例的 Token / 耗时下降至少 25%，Dynamic 全批
  Token 均值下降至少 10%”。这是待验证目标，不是承诺；若质量受损，不因达到成本目标而接受。

| 单例 Token / 耗时下降 ≥25% | **部分达成**：th=5 下 3003 −44.0%、3008 −21.9% |
| Dynamic 全批 Token 均值下降 ≥10% | 已达成（重放估计）：−12.3% |
| 延迟关键证据场景下的质量验证 | **未达成**：本批不含该类案例，见 P0-C 第 3 条 |

未达成的两项不计为“完成”。下一批（含延迟证据场景）应把它们作为运行前冻结的目标重新验证。

**交付物**

范围签名设计、覆盖状态说明、停止事件、回归测试、成本快照和独立批次结果。

### P0-C · 标签验收、未见案例与重复评测

**为什么做**

当前 10 个案例都已进入开发视野，标签仍是候选状态，每组合只运行一次。它们适合发现工程问题和
形成假设，却不足以证明架构的普遍优势。标签有误或案例与开发集同源，会直接放大错误结论。

这项工作与 P0-A、P0-B 并行启动，不必等所有工程优化完成后再开始。

**工作内容**

1. 对 Dev10 的候选 oracle 做独立人工复核与争议裁决，记录标签来源、可识别性、支持证据和审核人。
2. 评分同时检查最终服务 / 故障模式与证据链、引用和因果解释。猜中标签不能自动代表推理过程可靠。
3. 按故障家族与生成来源隔离开发、验证和测试案例，补充以下场景：
   - 证据不足；
   - 已观测的竞争机制；
   - 误导性变更；
   - 后期才出现关键证据；
   - 部分查询失败或分页未完成；
   - 修复、超时和恢复边界。
4. 已查看过的 Dev10 继续标为开发可见，不能改称盲测。现有材料也不能证明竞争机制案例恰好只有两例。
5. 在**当前代码与提示**上建立同期基线，避免把命名迁移、在途改动或提示变化算成优化收益。
6. 冻结代码、提示、模型、提供商路径、预算、缓存设置和随机运行顺序后开始比较。
7. 重复运行用于评估稳定性；三次可以作为开发起点，正式样本量、重复数、质量容忍界限和停止条件
   必须在看结果前确定。同一案例重复不是新的独立案例，temperature 0 也不保证完全确定。
8. 按案例或故障家族做配对分析，报告适用的置信区间。家族数量很少时，区间可能很宽，应明确说明。

**Fixed 补查实验**

现有结果只证明“一次固定批次在 3004、3005、3010 上不足”，不能证明“再加一轮固定批次必然无效”。
如果这个论证对报告很重要，可新增 `fixed_plus_one_round` 条件：

- 预先定义第二轮固定规则；
- 匹配总预算；
- 与单轮 Fixed 和 Dynamic 比较质量与全尝试成本。

若第二轮根据证据缺口选择任务，它已经是混合策略，应使用不同名称，并改写原 `fixed` 的含义。

**本轮已扩展的开发案例集（2026-11-01）**

第 3 条要求补充“竞争机制、误导性变更、证据不足”等场景，并把样本量从 10 提到 30–40。
本轮按**新增编码器血统**而不是改写旧编码器的做法完成，因此 `data/incidentbench_v16_dev`
（10 例，`causal-world-v1`）保持逐字节可复现：

| 项目 | v1（冻结） | v2-hardened（新增） |
| --- | --- | --- |
| 根目录 | `data/incidentbench_v16_dev` | `data/incidentbench_v2_hardened` |
| 编码器 | `causal-world-v1` | `causal-world-v2-hardened` |
| 案例数 | 10 | 36（`incident_4001`–`incident_4036`） |
| 判别难度开关 | 无（拒绝 `difficulty`） | `standard` / `boundary` / `competing` |
| 可识别 / 需弃答 | 8 / 2 | 29 / 7 |
| 覆盖标签 | 2 ordinary、2 misleading、2 missing、4 counterfactual | ordinary 21、misleading 2、missing 7、counterfactual 6 |
| 标签状态 | `pending/candidate-v1`，开发可见 | 同左，无人工验收 |

三个难度杠杆的含义：

- **`boundary`**：机制特征值恰好落在验收契约上，而不是远远越过它——`cpu_percent` 91（契约
  `>=90`）、`connection_count == connection_limit`、`p95_latency_ms` 3000、`duration_ms`
  1001（锁）/ 3001（慢查询）、`db_pool_max 20 -> 18`（契约只要求“低于并发数”，不要求大幅下调）。
- **`competing`**：可混淆的竞争机制在**自己服务**上发布一条症状记录，但从不发布它自己的判别
  证据；同时把晚期非因果变更放到**元凶自己的服务**上（比 v1 的网关干扰更诱人）。
- **`standard`**：幅度与 v1 相当，但带有竞争机制和同服务干扰，用来分离“幅度”和“竞争”两种难度。

**难度是怎么测出来的（以及为什么不能只看 mock）**

`MockProvider` 是**固定规则策略**，读取的正是 `guards.cause_discriminator` 的同一批契约判据，
因此它在四个难度臂上给出**完全相同**的结果（3 对 / 4 错 / 7 弃答），无法体现难度差异——
用 mock 通过率来宣称“案例更难”是无效的。本轮改用两个确定性读者直接测量：

| 读者 | v1 冻结 10 例 | v2-hardened 36 例 |
| --- | --- | --- |
| 契约读者（逐条核对 `cause_discriminator`） | 8 对 / 0 错 / 2 弃答 | 29 对 / 0 错 / 7 弃答 |
| 幅度读者（“真故障会给出夸张数字”的捷径） | 8 对 / 0 错 / 2 弃答 | 23 对 / **6 错** / 7 弃答 |

契约读者持平、幅度读者下降，这才是本轮的结论：**新案例对“只凭数值大小推断”的读法更难，
但对逐条核对契约的读法没有变难，也并非不可读**。它不构成对任何真实模型、盲测或生产表现的
结论。复算脚本：
[`measure.py`](../../analysis/wp_d/reports/hardened-difficulty-20261101/measure.py)、结果
[`results.json`](../../analysis/wp_d/reports/hardened-difficulty-20261101/results.json)。

**这条路线仍缺什么**

- 36 例仍是**开发可见**、候选标签、无人工验收；不能当作验证集或测试集。
- 两个编码器血统共享同一套队列 / 容量世界模型，不是独立故障家族；`manifest.json` 里 v2 的
  cluster 记作 `cluster_causal_world_v2_hardened`，但“独立来源”仍需 P0-C 第 3 条的切分设计。
- 未覆盖“后期才出现关键证据”和“部分查询失败 / 分页未完成”，这两类与证据护栏的交互是下一批
  的重点。

**四变体 mock 基线（仅证明流程可用，不证明难度）**

用正式实验装置（`run_incidentbench.py`，四条件协议、cache off）分别在两个数据集上跑了一遍，
结果见 [`mock-v1`](../../analysis/wp_d/reports/hardened-dataset-validation-20261101/mock-v1/aggregate.csv)
与 [`mock-v2`](../../analysis/wp_d/reports/hardened-dataset-validation-20261101/mock-v2/aggregate.csv)：

| 指标 | v1（10 例） | v2-hardened（36 例） |
| --- | --- | --- |
| 技术完成 | 10/10（四变体） | 36/36（四变体） |
| Dynamic 根因正确 | 4/8 = 0.50 | 12/29 = 0.41 |
| Dynamic 正确弃答 | 2/2 = 1.00 | 7/7 = 1.00 |
| Fixed-4 根因正确 | 0/8 | 0/29 |

Dynamic 与 Single、Full 在两个数据集上仍然**逐例相同**，Fixed-4 仍然全错——这与 v1 的结论
一致，说明新数据集没有改变 mock 的判定行为。**因此这张表不能用来宣称“难度提高”**：
mock 是固定规则策略，其正确率是数据里是否有契约判据的函数，与幅度和竞争无关。难度只能由上表
的两个确定性读者测出。

**完成标准**

- 标签状态、审核记录和争议处理可追踪。
- 开发、验证、测试案例的来源边界清楚，没有同一故障家族跨集泄漏。
- 所有计划槽位、重复运行和失败记录保留。
- 人工复核、三次重复或温度 0 都不会被表述为自动获得统计显著性。
- 新标签版本生成新评分产物，不静默升级历史候选评分。

**交付物**

标签审核清单、数据切分清单、冻结实验协议、同期基线、配对分析报告和已知局限。

## P1 · 在可信基线上提高效率

### P1-A · 按角色裁剪上下文与去除重复载荷

**为什么做**

Dynamic 的 Token 中约 74.8% 是输入，说明值得检查每轮是否重复携带 findings、观察、
候选假设和查询历史。但输入占比高不代表所有输入都可以删除；证据、反证、时间关系和权限信息
可能正是正确判断所必需的。

**现状**

`payload()` 已移除原始 events；部分角色使用证据目录而不是完整索引；分析阶段也已拆分提示
与身份上下文。因此下一步是审计和精确裁剪，不是重复实现已有做法。

**工作内容**

1. 分角色统计每个输入字段的长度、出现次数和跨轮重复率，覆盖 Coordinator、专家和 Verifier。
2. 先用确定性投影与去重，优先保留：
   - 当前任务相关观察；
   - 候选之间真正不同的证据；
   - 关键反证和竞争机制；
   - 尚未关闭的缺口；
   - 必要的覆盖摘要和证据 ID。
3. 原始材料继续保留可追溯路径；权限内确实需要时再取。不能只发增量而丢失判断所需的历史。
4. 压缩不得删除不利证据、时间关系、失败 / partial 状态、来源标识或权限边界。
5. 如果使用 LLM 生成摘要，把摘要调用成本、摘要误差和新引入的不一致一并计入实验。
   默认先比较确定性裁剪，再考虑模型摘要。

**完成标准**

- 报告分角色输入 / 输出 Token、请求、延迟和全流程总量。
- 质量、引用完整性和门控结果通过共同回归及新案例检查。
- 以全流程总消耗评价，不用单次 prompt 变短作为唯一成功标准。
- 未验证前不承诺固定节省百分比。

**交付物**

字段使用矩阵、裁剪开关、单变量对比结果、质量与引用回归报告。

### P1-B · 判别价值派单、成本预算与及时定稿

**为什么做**

动态架构的价值不是“每轮派更多人”，而是把有限的调查用在最可能改变判断的证据上。
系统还应在已有候选满足现有门控时及时定稿，并预留完成协调、STOP 和恢复所需的预算。

**现状**

Coordinator 已能动态派发 1–2 个任务，并有限制重复任务和预算的基础逻辑。CAES 已有候选生成、
成本评分和 shadow 原型，但当前明确只支持 `full`；不能只在 Dynamic 配置中打开开关就宣称生效。

**工作内容**

1. 每个候选任务说明：
   - 补充哪个缺口；
   - 哪些可能结果会改变候选排序；
   - 预计请求 / 工具成本；
   - 是否已被完整覆盖；
   - 是否必须等待其他任务的结果。
2. 优先有区分能力的检查，减少只增加同症状记录的同质查询。有限预算下可只派一个决定性任务，
   不必每轮填满两个名额。
3. 把修复、实际 HTTP 请求、复核和 STOP 的成本都计入预算；为收尾流程保留最低额度。
4. 独立任务可以并行，存在数据依赖的任务保持顺序，确保共享状态不会发生竞态或覆盖。
5. 适配 CAES 到 Dynamic 时，显式处理角色、复核预留、恢复与协议契约；启发式分数不能称为
   校准的信息增益或成功概率。
6. 先记录 shadow 建议，再作为独立派单条件测试。不要一次同时改变覆盖规则、上下文和派单策略。

**完成标准**

- 单独完成 P0-B 与 P1-A 的消融，再验证组合效果。
- 报告所选任务、关键证据获取率、重复查询、错误弃答和全尝试成本。
- 候选满足 FinalizeGate 时，不能因为继续填满任务名额而延迟定稿。
- CAES 在 Dynamic 上的实际生效路径有测试，不只检查配置文件被解析。

**交付物**

派单决策字段、成本预留规则、shadow 记录、独立实验条件和消融报告。

## P2 · 在条件成熟后验证增强能力

### P2-A · 按需独立复核

**目标**

把独立复核从 Full 中的“每次都做”，改成只在高风险状态触发。要检验的是复核是否真正改变结论，
而不是证明“多一个模型角色看起来更严谨”。

**候选触发信号**

- `competitor_assessments` 出现 `observed_competing_mechanism`；
- 候选存在已观测的 `against_ids`；
- 候选缺少时间兼容的跨源佐证，却准备定稿；
- 后续实验发现、且不依赖模型自报置信度的其他确定性信号。

这些信号来自共享状态，触发原因可以复算。它们不等于“一定需要复核”：缺少观测可能更需要专家
取证，竞争机制与反证也不能靠一段复核文字自动消失。

**工作内容**

1. 新建独立条件，暂称 `dynamic_review`；不改变 `dynamic`、`full` 或冻结条件名的含义。
2. 设计阶段明确三种动作的边界：再取证、复核已有证据、正常弃答。
3. 不能只增加 `verify` 路由。还要设计复核反馈、候选 / 证据指纹失效、复核次数上限、预算预留、
   超时与失败、checkpoint / resume 和停止规则。
4. 两组保持相同的基础归因门槛。复核没有新证据时，不能覆盖确定性反证阻断。
5. 如果新条件要求复核通过才能定稿，要明确这是一道额外门槛，并报告它可能带来的漏判。

**完成标准**

- 在包含真实竞争机制和矛盾的未见案例上，配对比较 `dynamic`、`full` 与 `dynamic_review`。
- 报告触发率、各触发原因、复核改变结论的次数、纠正与引入错误、条件成本和全批成本。
- 触发率低只表示本批不足以评估；触发本身不证明复核有效，也不预设混合方案优于 Dynamic。

**交付物**

协议、实现开关、触发审计、失败与恢复测试、配对实验报告。

### P2-B · 提供商路径与结构化输出可靠性

**为什么做**

即使推理质量不变，格式错误、提供商兼容问题和重跑也会消耗时间与 Token，并使首次完成率下降。
这项工作的目标是让失败可见、可恢复，同时保持严格输出契约。

**现状**

阶段提示拆分、分析阶段精简身份上下文和 DSML 定向修复已在源码中存在，不再作为“待开发功能”重复列出。
此前网关审计记录了旧故障范围，见
[网关 JSON 原因审计](../../analysis/wp_d/reports/local-gateway-json-audit-20261031/report.zh-CN.md)；
后续完整批次的失败情况应单独统计。

**工作内容**

1. 除连通性检查外，增加复杂 `InvestigatorPlan` 与 `AnalysisOutput` 的兼容性探针。
2. 记录首次合法率、有限修复成功率、终止失败率、失败类别和修复成本；保留 schema、身份和引用校验。
3. 网关模型别名不一定完整描述实际路由。在可观测范围内记录实际提供商、模型和配置；
   自动路由无法固定时明确写出未知项，不用别名冒充精确身份。
4. 只保存脱敏后的输出形态与错误诊断，例如 DSML / tool-call-like、截断、错误位置和
   `finish_reason`；不自动执行模型返回的工具标记。
5. 不用无限重试提高“最终完成率”。传输、格式、业务校验和进程中断分别归因。

**完成标准**

- 在新目录中验证复杂请求和有限恢复，技术失败与正常弃答分开。
- 全尝试成本进入共同账本。
- 当前批次若出现阻断性新失败，本项立即上调为 P0，优先于性能优化。

**交付物**

能力探针、脱敏诊断样例、路由记录、恢复测试和失败成本报告。

## P3 · 架构稳定后的成本与延迟探索

以下方向目前没有足够证据要求优先实施，应在 P0/P1 的结果稳定后逐项测试。

### 模型分工与路由

测试低成本模型处理计划或局部分析、较强模型处理困难归因。先保持同模型架构对照，
再比较路由策略；计入升级、修复和失败成本。

### 缓存

探索确定性结果或合法分析的安全复用。缓存键必须绑定模型、提示、任务、公开数据版本和权限范围。
Benchmark 主对照仍保持 cache off；缓存实验单列命中率、失效行为、冷热成本和质量影响。

### 并发

分别调节批次并发与单次调查内的独立任务并发，测尾延迟、限流和吞吐。提高并发可能缩短批次墙钟，
却不一定减少请求或 Token；预算与共享状态隔离必须保持。

这些方向不要与派单、上下文或模型切换同时改变。每次只引入一个主要变量，才可能解释结果。

## 执行顺序

| 阶段 | 要完成的事 | 通过条件 |
| --- | --- | --- |
| 1. 基础 | P0-A 指标对账；P0-C 标签复核、数据准备与同期基线 | 原始记录可复算；标签与数据边界可追踪 |
| 2. 收敛 | P0-B 覆盖、去重和停止规则，单独实验 | 质量不越过预定门槛；停止理由与成本可审计 |
| 3. 效率 | P1-A 上下文裁剪；P1-B 派单策略，分别消融 | 各自有单变量结果；组合后无质量回归 |
| 4. 外部验证 | 冻结候选方案，在未见案例上配对、重复评测 | 标签、协议和分析方案已预先冻结 |
| 5. 条件增强 | 根据证据开展 P2-A、P2-B 或 P3 | 有独立条件、明确收益假设与失败边界 |

### 建议责任分工

| 角色 | 主要职责 |
| --- | --- |
| 技术负责人 | 代码路径、开关、恢复与兼容性；保证实现不依赖 oracle 或案例特判 |
| 测试负责人 | 回归、协议检查、独立复算、失败保留与批次运行 |
| 数据 / 标签负责人 | 标签审核、案例来源、故障家族切分与盲测边界 |
| 报告负责人 | 指标口径、质量与成本双轴报告、限制和反例 |
| 全组 | 冻结比较方案、审阅结论、确认 PPT / Demo 与文档中的表述边界 |

建议负责人可以兼任，但每项交付物应有明确的最终审阅人。工程实现者不独自决定收益是否成立，
测试或报告负责人应能独立复算关键结果。

## 统一工作规则

### 实验前

- 写清要改善的现象、预期机制、比较条件和停止条件。
- 冻结模型、提供商、提示、预算、评分和重复数。
- 为收益设置开发目标，为质量设置容忍界限；不要只看结果后再定义成功。

### 实验中

- 新批次使用新目录，保留所有 attempt、失败、中断和未知 usage。
- 模型与工具输入不读取 evaluator-only oracle。
- 除明确研究的变量外，保持其他条件一致。
- 不因结果不利而中途改提示、换标签或择优重跑。

### 实验后

- 先检查技术完成、协议、来源不变和成本完整性，再比较质量。
- 报告正确归因、错误归因、正确弃答、错误弃答、技术失败和首次完成率。
- 同时给出条件成本与全批成本；失败 attempt 不能从分母消失。
- 未达目标、触发率为零、质量下降和失败样例都要归档。

### 对外表述

可以写：

- “在候选标签下的 10 个开发案例中，Dynamic 与 Single、Full 的质量分数相同，资源更低。”
- “本批未观测到 Full 的额外质量增益，因此暂不默认开启独立 Verifier。”
- “Fixed-4 成本最低，但在三个可识别案例上错误弃答。”
- “证据缺口护栏在冻结轨迹上重放：两个高成本弃答案例合计 Token 下降 32.8%，全批 −12.3%，
  且不影响任何可识别案例的最终结论。”
- “新增 36 个开发案例，其中 29 个可识别、7 个需弃答；对‘只看数值大小’的读法，正确率从
  8/8 降到 23/29，而对逐条核对契约的读法保持 29/29。”

暂不能写：

- “Dynamic 已被证明在统计上优于其他架构。”
- “Verifier 永远无用”或“Dynamic 可以保证生产准确率”。
- “40/40 技术完成等于 40/40 诊断正确。”
- “Fixed 加一轮一定无效”或“三次重复就自动显著”。
- “模型别名就代表已经精确记录实际提供商和模型。”
- “新增数据集证明系统能处理更难的故障”或“36 例已达到统计显著性”。
- “证据缺口护栏已在真实批次上验证过成本收益”——目前只有轨迹重放，且 `max_rounds: 4`
  的默认配置下该阈值不会触发。

## 名词说明

| 名词 | 通俗解释 |
| --- | --- |
| `dynamic` | 当前主架构：根据缺口动态派专家，最后由确定性门控检查能否接受根因 |
| `full` | 与 Dynamic 相同的调度，额外要求独立 Verifier 复核 |
| Single | 一个身份使用全部工具，自己规划、查询和自我反思 |
| Fixed-4 | 首轮固定派出四类专家，不会按新缺口继续定向补查 |
| Verifier | 独立读取共享证据、质疑候选并提出补查的角色 |
| FinalizeGate | 不接受根因前的确定性检查，核对引用、来源、机制和竞争假设 |
| 可识别案例 | 数据中存在可支持唯一根因的案例 |
| 正确弃答 | 证据确实不足时，正常结束并明确 `INCONCLUSIVE`，不编造根因 |
| 技术完成 | 运行正常结束且协议有效，不等于诊断正确 |
| 候选 oracle | 当前使用的待人工确认参考标签，不等于正式标准答案 |
| 全尝试成本 | 包含失败、修复、中断和成功 attempt 的总成本 |
| 输入 Token | 每轮发给模型的上下文消耗；输出 Token 是模型生成内容的消耗 |
| 查询覆盖 | 某工具在某服务、时间、过滤和分页范围内是否真正完成；空结果不等于健康 |
| 判别证据 | 能改变候选根因排序或排除某个机制的证据 |
| 消融 | 只增加或移除一个机制，观察它是否真的带来质量或成本变化 |

01

先看这一段

30 秒理解这个项目

不需要读代码，也能向别人讲清楚它是什么、为什么这样做、现在做到哪一步。

问题 事故复盘最怕“自信地猜错”

判断根因要交叉核对日志、指标、数据库和变更记录。通用大模型很容易把相似症状讲成一个顺口的故事， 却给不出引用，也不愿承认证据不够——在生产环境里，这种过度断言比“查不出来”更危险。

做法 分工取证，按缺口派单

四类专家各自只碰自己的证据域；协调者每轮只安排最关键的下一两项检查； 调查结果先经过确定性合并，再由门控验收。Verifier 是可选消融，不是默认路径。

证据 144 个槽位，零误判

在 36 个硬化开发案例上，Dynamic 取得 33/36，是四架构最高；技术上完成的 33 次全部判对。 19 次可识别失分全部以 INCONCLUSIVE 结束，没有一次给出错误根因。

一句话版本：它不是一个“更会聊天”的 Agent，而是一套有证据边界、有验收门控、 并且允许弃权的排查流程。我们比较的不是“模型数量”，而是分工与协调方式。

Agent 流设计

证据如何流经角色

九个 LangGraph 节点里，只有调查、协调与可选的 Verifier 调用模型； Merge、FinalizeGate 和 Reporter 都是确定性组件——这是“协作”与“多个模型各说各话”的关键区别。

协作不是“自由聊天”

  • 调查员只写局部结果。并行任务不能直接覆盖共享状态。
  • Merge 先校验再发布。身份、角色、实际查询账本、引用来源缺一不可。
  • 协调者只看已发布内容。看不到未经验证的原始猜测。
  • Verifier 只能取授权 ID。候选或证据一变，旧审查指纹立即失效。
  • 门控拥有最终决定权。模型说“是”不算数，门控接受才算数。

为什么这能减少过度断言

每个结论都必须指向具体记录；每次查询都有账本；证据不足时没有“补全故事”的通道。 这套契约把“引用或弃权”从提示词里的建议，变成了运行时无法绕过的门控。

对外可以这样解释：不同调查员各看一类证据，协调员只安排下一两项最关键的检查， 结果要经过合并和验收才能写进报告。

05

怎么读失分

零误判，以及 8 次技术失败

这两件事必须一起讲：前者说明系统“答的时候是准的”，后者说明批次并非全部顺利， 但失败被如实保留，而不是被替换成好看的一次。

19 次可识别失分，没有一次给出错误的 culprit_service / failure_mode。

它们全部以 INCONCLUSIVE 结束，属于“过度弃答”。7 个不可识别案例在所有完成的运行里 都正确弃权。失分模式是召回不足，而不是编造根因——对“引用或弃权”契约来说，这是比总分更强的证据。

可以讲：系统在证据不足时会明确弃权，而不是猜。
不能讲：“136/144 技术完成等于 136/144 诊断正确。”

8 次技术失败（5.6%）

结构化输出无效：5 次响应包缺少字符串内容，1 次输出被截断且修复后仍无效，schema 校验失败。

6 次

Finding 身份不匹配：工具返回的记录与本轮身份不符，被确定性门禁拦下。

2 次

分布：Single 1、Fixed-4 2、Dynamic 3、Full 2。四个架构都有，说明这是 provider / 结构化输出层的 偶发问题，不是某一架构的设计缺陷。按批次预案未重试，失败槽位保留在分母中；失败尝试消耗 92.2 万 Token，占全部的 3.8%。

batch_finished_with_errors 退出码 1 是合法终态

证据边界（必须随数字一起引用）

  • 不是盲测：协议为 formal: false、blindness_level: development_visible。
  • 标签是临时的：所有 oracle 的 annotator_status 为 pending，人工复核后判定可能变化。
  • 单次重复、单模型、36 案例：上表差异是描述性的，不做显著性推断。
  • 输入未漂移：144/144 槽位记录 source_unchanged: true；这项校验覆盖仓库输入，不覆盖网关侧路由。
  • 技术失败留在分母：“质量成功/36”是失败包含口径，“完成内成功率”另列。

快速上手

按你的角色开始

不用从头读完全文。选一个角色，这里只放你明天就会用到的内容。

你只需要记住三句话

  1. 四类调查员各看一类证据，协调员只安排下一两项最关键的检查。
  2. 调查结果要经过校验、合并和门控验收，才能进入最终报告。
  3. 证据不够时系统会说“查不出来”，而不是编一个根因。

遇到数字怎么解释

  • “33/36”是 36 个案例里答对或正确弃权的数量，不是准确率承诺。
  • “零误判”指没有一次给出错误根因；失分都是该答而弃答。
  • “比 Single 省 39%”指平均耗时和 Token，不是成本账单或生产结论。
  • 这是开发集、单次重复、临时标签，属于描述性开发证据。

可以讲的

  • Dynamic 是四架构里质量最高的一档（33/36）。
  • 技术上完成的 33 次全部判对；19 次失分全是弃答。
  • 竞争性成因 7/7、反事实配对 6/6，是硬化集新增难点上的最好成绩。

不要讲的

  • “多 Agent 已达到统计显著优势。”
  • “Dynamic 在盲测或生产中一定更准确。”
  • “修复建议已执行 / 生产事故已恢复。”
  • “Mock 结果证明真实模型能力。”

验收标准

  • 每个槽位都有终态；batch_finished_with_errors 是合法终态，不是崩溃。
  • 成功 attempt 的 scope/trace/result 身份一致，verification 通过协议与 STOP 检查。
  • 失败 attempt 保留在 batch-state.json 与分母中，不重试、不替换。
  • 成功均值不混入失败 attempt；质量按 evaluator oracle 离线评分。
  • 当前测试基线：2026-11-02 对最终代码树全量重跑 1179 通过、3 跳过、0 失败（463.23 s，退出码 0），日志 analysis/submission/pytest-20261102.log；代码再变动就要重跑并更新记录。

推荐叙事顺序

  1. 问题：RCA 要跨四类证据交叉验证，单 Agent 容易塞满上下文或过度断言。
  2. 设计：角色 ACL、按缺口派发 1–2 个任务、Merge 发布、共享证据板、确定性 FinalizeGate。
  3. 方法：36 个硬化开发案例 × 四架构 = 144 槽位，同模型、同工具、同预算、cache off。
  4. 结果：136/144 技术完成；Dynamic 质量 33/36，完成内 33/33。
  5. 失败：零根因误判，19 次失分全是弃答；Fixed-4 错弃 12 个；Full 多耗 56.7% Token。
  6. 限制：开发可见、标签 pending、单次重复；下一步送审、重复评测、blind Test。

两个口径不要混

  • 质量成功：分母 36，技术失败算未成功 → Dynamic 33/36。
  • 完成内成功率：只在技术完成的运行里算 → Dynamic 33/33。
  • 正文每个结论都要能指回表格、报告或证据文件。
  • 不要只报平均值而隐藏错误案例、失败槽位和重试成本。

现场问答准备

为什么不直接用一个更大的模型？
单 Agent 仍可做基线，但动态分工减少无关上下文和查询；本批 Dynamic 质量更高（33 vs 32），耗时和 Token 各低约 39%。
多 Agent 的优势是不是因为模型变多？
不是。优势来自专家边界、按缺口派发、校验合并和明确弃答；Full 多一个 Verifier，反而少 3 个成功、多耗 56.7% Token。
为什么 Fixed-4 更便宜却正确率低？
它只做一次固定批次，不能根据缺口补查；27 个可识别案例上错弃 12 个（4001、4006、4007、4008、4014、4019、4020、4023、4024、4025、4035、4036）。
为什么批次以“有错误”结束、退出码是 1？
8 个槽位发生技术失败（6 次结构化输出无效：5 次响应包缺少字符串内容、1 次截断且修复后仍无效；另 2 次 finding 身份不匹配），batch_finished_with_errors 是协议允许的合法终态。按预案不重试、不替换，失败保留在分母；分布覆盖四个架构，属 provider 层偶发问题。
Dynamic 没有 Verifier 是否风险更高？
它仍保留 Merge 校验、确定性接地和 FinalizeGate；本批 Dynamic 是四架构最高（33/36，完成内 33/33）。Verifier 对更难竞争假设的独立价值需要更大数据验证，按需 Verifier 是后续实验。
数据是否独立盲测？
不是。36 个 Dev 案例为 development_visible，oracle 的 annotator_status 仍是 pending，每案例一次；结论是描述性开发证据。
弃答是不是失败？
在无足够证据的案例中，明确弃答是正确业务结果；Provider、网络或预算失败才是技术失败。本批 19 次可识别失分全是弃答，没有一次根因误判。
下一步最重要的验证是什么？
先把 oracle 标签送人工复核、做重复评测并划分 blind Test 分区；再验证搜索收敛、上下文裁剪与判别价值派单。按需 Verifier 在代表性困难案例准备后再测试。

## 1. 目标与现状边界

长时测试不能只在最终结束时保存一份报告。必须能回答：进程是否存活、调查是否推进、当前等待什么、最近完成了什么、消耗了多少预算，以及异常发生前最后一个可靠状态是什么。

当前 T6 runner 在开始时写入 scope，主要在调查返回后保存完整 trace、报告和 verification。外部可检查进程和退出日志，但缺少持续落盘的调查事件、可靠中间检查点和业务进展状态。硬终止可能丢失尚未落盘的上下文。现有 Mock resume、离线 checkpoint continuation 与未来真实请求恢复必须分别标识；已有真实 benchmark resume 仍按现有守卫拒绝，不能因本计划直接开启。

本迭代只增强记录、诊断和经过验证的恢复机制，不修改诊断正确性标准、证据权限、Verifier、FinalizeGate 或 STOP 协议。

## 2. 产物与一致性合约

以下文件名和字段为拟定接口，实现前需冻结 schema_version 和兼容策略。

| 产物 | 保存内容 | 写入时机与用途 |
|---|---|---|
| `run-manifest.json` | run/batch/attempt 身份，源码、依赖、配置、Prompt、数据、模型及协议哈希，启动参数与恢复父记录 | 首次请求前持久化；后续只追加有版本的 provenance，不覆写原冻结依据 |
| `events-*.jsonl` | 有序运行事件、阶段、任务、逻辑调用、物理发送、工具结果引用、决策、重试、错误、STOP | 事件发生时追加；不是等待整轮调查结束 |
| `status.json` | 生命周期、当前阶段、活跃调用、最后心跳、最后业务进展、已知预算与用量完整性 | 原子更新；供终端、UI 和人工检查 |
| `checkpoints/` | 已提交的调查状态、任务状态、证据索引、审核状态、计数器，以及对应事件序号、偏移和哈希 | 安全阶段边界保存；至少保留上一份有效检查点 |
| `attempts/` | 每个物理请求的准备、发送、返回、失败及 reconciliation 元数据，受控的调试附件 | 在发送前记录意图，在返回或异常时补记结果 |
| `stdout.log`、`stderr.log`、退出记录 | 启动、退出码、已清理的异常类型与栈、supervisor 检测结果 | 持续保存；作为异常定位的辅助证据 |
| 最终 trace、report、verification | 完整结果及最终事件/检查点绑定 | 正常结束或可处理异常时汇总；保留已有消费者的兼容性 |

一致性要求：

- 事件包含唯一 event_id、单调递增序号、run_id、attempt_id、时间和 schema_version；逻辑调用与物理 HTTP 尝试分别编号。
- 请求开始事件必须先于实际发送持久化，结束事件与用量 reconciliation 分别记录。写入失败不能悄悄继续发起新的付费请求。
- 关键事件 flush 并按约定 fsync；检查点在同一文件系统临时写入、校验后原子替换。明确断电保护边界，不承诺操作系统无法提供的零丢失。
- 检查点绑定已提交事件前缀。恢复只从一致前缀开始；不能将部分新状态与旧计数器拼接。
- JSONL 尾部残缺、磁盘满或损坏时保留原文件和错误证据。使用校验后的新分段，不静默截断原始记录或重建成“成功”。
- 心跳允许限频和合并，关键请求、状态提交、错误与终止事件不得被限流丢弃。记录开销与磁盘增长须有界。

## 3. 活性、进展与异常诊断

必须分别展示三个维度：

1. **进程活性**：supervisor 观察的 PID、启动身份、退出状态；防止 PID 重用被误认成原运行。
2. **执行阶段**：等待模型、执行工具、合并、审核、停止、保存等；活跃调用显示开始时间和 deadline。
3. **业务进展**：最后完成任务、最后新增证据、最后状态提交时间；心跳不能冒充新证据或有效调查进展。

建议心跳间隔 10 秒，连续缺失 3 次标为“心跳缺失/需检查”，该阈值在实现时配置和冻结。模型请求在其 deadline 内等待属于可解释等待；同一已完成查询反复执行、长时间没有状态提交、请求超过 deadline 则分别告警。告警本身不能直接证明死锁或网络根因。

supervisor 与调查主循环分离，能够发现事件循环卡住或子进程退出。只读状态查询不得触发 Provider、工具调用或自动重试。初期优先提供命令行状态和文件证据，Web 展示后续接入同一合约。

可捕获异常应尽力保存最后有效检查点、错误阶段、清理结果和退出记录。SIGKILL、强制结束和断电不能依赖 finally；supervisor 应依据既有日志将其记为异常中断。日志可说明最后一次已知行为，无法确定的底层崩溃原因应保留为未知。

## 4. 检查点的安全边界

优先在工具结果提交、MERGE 完成、协调决策提交、Verifier 结果提交及 STOP 协议阶段推进后保存。请求正在发送时只保存发送意图和 pending 状态，不能伪造响应。

检查点至少包含：

- 公共调查状态、公开证据内容或不可变内容引用及校验和、已完成和待执行任务。
- Graph 所处节点、下一可执行边界、review 与 hypothesis/evidence 快照绑定、STOP/取消状态。
- 已消耗的物理请求许可、工具/轮次/Token 计数、未知用量标记、重试与 repair 计数。
- 累计已用时间、原始 deadline、最后持久化时间、恢复次数及 checkpoint 父链。
- 去重、发现阶段、已完成查询等影响后续执行的运行时状态；不能仅保存 report 或 schema 内的可见 state。

已发出 STOP、用户取消或进入不可恢复失败的运行不得自动恢复调查。审核状态过期时必须重新审核；恢复不能重用对不同证据/假设快照的 sufficient verdict。

## 5. 分层恢复与实验口径

### R0：只读回放与 Debug

从事件前缀和检查点重建最后可靠状态，展示 pending 请求、最后成功阶段和预算。零 Provider、零工具调用；不把缺失历史从最终结果倒填出来。

### R1：批次级续跑（优先交付）

从批次 ledger 恢复尚未开始的 case × variant × repeat，保持原冻结顺序和配对。已完成项校验后跳过；失败和中断项保留原记录与分母，不静默重跑。若决定重跑失败项，创建新的 attempt 并记录原因、父尝试和完整成本，不能替换原尝试。

### R2：单次调查内续跑（后续交付）

仅在已验证的安全边界恢复。恢复前必须校验源码、依赖、模型参数、Prompt、数据、工具权限、协议、事件/检查点哈希和预算；漂移、损坏、已有并发执行者时拒绝恢复。源码变更后的继续执行属于新实验条件或单独 Debug continuation，不能冒充原冻结实验。

外部请求存在不可消除的模糊窗口：服务端可能已经处理，客户端却未持久化结果。不得宣称 exactly-once。若 Provider 无可验证的幂等/结果查询能力，将请求记为 outcome unknown、用量可能不完整；显式决定失败终止或创建新请求尝试，保留潜在重复成本。未来有副作用的工具需另行设计幂等和对账，本迭代不自动重放此类工具。

预算跨重启累计，不能通过 resume 重置许可、轮次、Token 或重试额度。默认原始 wall deadline 继续有效，停机时间也计入；如另设 active-time 模式，必须在实验前统一声明并单列实际 elapsed time。时钟异常时保守拒绝恢复，不能凭重置 monotonic clock 获得新预算。

### 结果标签与统计

- 区分 `fresh_live`、`resumed_live`、`offline_replay`、`debug_continuation`，保存父子 attempt 身份。
- 原始失败、中断、未知请求与恢复后的额外开销全部保留；分别报告原始尝试分母和恢复策略后的结果。
- 不将 resumed_live 或离线续跑追认为原 G1a 的从头真实验收；如需接受恢复实验，必须先修订和冻结对应协议。
- 四架构必须使用相同观测、记录、检查点和恢复策略。运行中不得仅给某一架构增加重试或恢复机会。

## 6. 数据与安全边界

日志不记录 API key、Authorization、环境变量值、私有 Oracle、隐藏推理或未授权的证据。默认保存可审计的元数据、公开证据引用和已清理错误；完整原始请求/响应若确需调试，应使用受限附件与明确保留策略，不能直接进入公共报告或 Git。

实时状态和 Replay 继续执行 run/incident 权限检查、路径校验、内容转义和 Oracle 隔离。日志导出、保留与清理应显式区分历史原始实验依据和可清理的派生缓存。

## 7. 实施顺序与交付门槛

| 阶段 | 交付 | 验收条件 |
|---|---|---|
| O0 | 当前事件、请求许可、Graph 状态和 runner 保存路径盘点；冻结持久化合约 | 明确现有接口、缺失状态、并发写入模型及与旧 trace 的兼容方式 |
| O1 | 增量事件、独立心跳、状态读取、请求前置记录 | 调查尚未完成即可查看阶段和最后进展；读取状态不新增模型/工具调用 |
| O2 | 原子检查点、崩溃记录、R0 Debug | 强制结束后仍可定位最后可靠边界；损坏状态不会被当成可恢复成功状态 |
| O3 | 批次 ledger 和 R1 续跑 | 跳过已完成项且不重复调用；失败分母、执行顺序、配对和预算口径保持正确 |
| O4 | 有限安全边界的 R2 单调查恢复 | 模糊外部请求明确标记；漂移/损坏/并发/STOP/取消均拒绝非法恢复 |
| O5 | 独立复核、受控真实小验收、报告与 Web 状态接入 | 离线故障注入先通过；真实运行单独授权、冻结并记录，不冒称现有能力 |

O1/O2 应成为后续扩大真实批量实验的工程前置条件；R1/R2 按验收成熟度启用，不能仅因已有 checkpoint 文件就开放真实 resume。当前已启动的冻结 T6 不热修改、不补造中间态；本计划不要求中断该运行，也不替代它的实际验收。

## 8. 必须覆盖的验证场景

- 正常长调查：中间事件可见；心跳与实际进展能区分；最终 trace 与事件日志一致。
- 模型超时、重试、schema repair、工具错误：每次物理发送可追溯，预算不重复补发或清零，未知 Token 保持未知。
- 查询完成但分析未完成、MERGE 提交前后、review 刷新、STOP 各阶段：分别故障注入并验证恢复边界。
- 主循环卡住、未捕获异常、强制结束、磁盘满、部分写入、损坏检查点、时钟异常、双进程争抢恢复。
- checkpoint 与日志偏移/哈希不匹配、源码/数据/协议漂移：拒绝继续并保留原证据。
- 批次已完成项不再调用 Provider；失败/中断项不从分母消失；重新尝试有独立身份。
- 已取消或 STOP 后不再调查；恢复后的证据与假设变化要求有效的新审核。
- 日志、状态页和导出负例：secrets、Oracle、越权证据、路径穿越和脚本内容不得泄漏或执行。
- 四架构记录与恢复策略一致；测量并报告记录开销、日志大小及留存策略。具体性能阈值在 O0 基线后冻结，不能凭计划虚报。

交付需包含：版本化 schema、使用说明、故障注入测试与原始日志、恢复前后计数核对、已知不可恢复窗口、完整回归和独立复核记录。只有实际通过的阶段才能标为完成。

# 第四轮 HTTP 429 原因调查（只读）

结论：现有证据不支持“本批次自身超过截图所示 RPM 上限”为主要解释。HTTP 429 来自实际 HTTP 响应，不是本地预算器把其他错误转换成 429。具体是哪条服务商规则触发，仍被现有诊断字段限制，不能编造为已经确定的上游拥塞。

## 已定位的本地行为

1. provider.py 构造请求后读取 HTTP status 和响应 error.code。rate_limit_exceeded 是服务商响应中的允许保留代码，并非根据并发猜测生成。429 与本地 request/token/wall budget 是不同的分类路径。
2. 响应正文只提取 error.code；error.message、error.type、详细额度字段及 request-id/rate-limit 响应头不进入 FailureInfo。现有记录仅有解析后的 retry_after_seconds=null；无法由此证明服务器完全没有发送相关头，也无法恢复已丢弃的响应正文。
3. 冻结请求体没有显式 max_tokens/max_completion_tokens，因此“客户端把最大输出设得过大”没有代码依据。不过服务商对省略该字段采用何种预留规则尚未知，不能排除其默认行为。
4. 除 single 外，dispatch 通过 asyncio.create_task/gather 并行内部任务。外部两个槽位本轮最多产生四个同时在途请求。single 的任务串行，slot-004 也失败；只用内部并发不足以解释全部 429。
5. 恢复策略对每个逻辑调用分别执行 2s/4s 重试，无 jitter；此路径未发现跨调用或跨进程共享的限速/冷却器。78 次 429 中有多次短期恢复，但任一关键调用连续三次失败仍使整个调查技术失败。它解释为何调查推进更深却仍可能最终失败，不证明原始限流的服务端原因。
6. 事件中另有两次 SCHEMA_VALIDATION_FAILED（slot-001、032），是中途出现的不同错误；十个新 attempt 的终止错误仍是 429，不能把 schema 作为本轮共同终止原因。

实际 endpoint 主机为 discovery-api.intern-ai.org.cn，与原批次匹配。TokenPlan 官方页面明确所有 API Key 共享账户的 RPM/TPM，调用合并计算：
https://discovery.intern-ai.org.cn/token-plan/home

因此同一账号新建 key 不能隔离此限额。另一个通用 API Key 帮助页的 500 RPM 指标属于其他页面/服务上下文，不用它覆盖用户 TokenPlan 截图。公开检索未找到该具体模型的可核实专属限制，不能把 50/200 RPM 当作已经核实的该模型唯一规则。

## 原因排序与边界

- 优先核查账号所有 key 的合并流量，以及该模型/上游通道的额外限流与容量规则。这两类均能解释本批次只有 18 RPM 却出现大量快速 429；现有日志无法在二者中定案。
- 短窗口突发、在途请求约束、TPM 预留口径仍可能参与，但尚无直接限流字段证明。
- 请求构造、鉴权、结构化协议完全不被支持，不是共同终止原因的有力解释：相同冻结配置存在大量成功调用，且 22 个逻辑调用在重试后恢复。
- HTTP_PROXY/HTTPS_PROXY 在当前审计进程中存在，provider 对此主机 trust_env=true；这只是可见的路由条件，既不能追溯证明每个历史 worker 的代理值，也不能证明代理制造 429。未修改或测试代理。
